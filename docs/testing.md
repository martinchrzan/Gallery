# Tests

Three layers, none of which need anything running first except the last, which starts what it needs.

```bash
npm test           # unit + integration, both workspaces
npm run test:e2e   # end-to-end, needs `npm run build` first
```

| Layer | Where | Runner | Count |
| --- | --- | --- | --- |
| Server unit | `server/test/unit` | Vitest | 67 |
| Server integration | `server/test/integration` | Vitest + `app.inject()` | 70 |
| Web unit | `web/test` | Vitest | 73 |
| End to end | `e2e` | Playwright | 58 |

## No real photos, ever

Every layer runs against a library written by [`tools/fixture-library.mjs`](../tools/fixture-library.mjs):
generated landscapes with real EXIF — capture dates spread over four years, camera makes and models,
exposure triangles — laid out in nested folders, plus a RAW file the gallery cannot thumbnail and a
text file that is not media at all.

It is seeded, so two runs on the same day produce identical files. It also always writes photos dated
exactly one and two years ago today, so the "on this day" strip has something to show whenever the
suite runs.

The same generator produces the library behind the README's screenshots, which is why those can be
regenerated by anyone without a photo of theirs ending up in the repository.

## Server unit tests

The pure logic, with the security-relevant parts covered hardest:

- **`paths`** — the containment guard. Traversal in every spelling, drive letters, NUL bytes, and the
  reduction of a client-supplied name to a bare path segment (reserved device names, trailing dots,
  dotfiles, the Windows-forbidden set).
- **`scope`** — the authorization logic. That `Travel` does not match `Travel-private`, that an empty
  selection means an empty gallery rather than the whole library, and that a folder genuinely called
  `100%_backup` does not become a SQL `LIKE` wildcard.
- **`metadata`** — the filename date parser, including the shapes phones actually produce and the
  guard against reading an unrelated run of digits as a future capture date.
- **`auth`** — code generation: the alphabet, the grouping, that codes do not repeat, and that
  normalisation is idempotent so hashing and verifying cannot drift.
- **`uploads`** — what may be written into a photo library through a web form.

## Server integration tests

The real Fastify app — same plugins, same root authentication hook, same error handler — built by
`buildApp()` and driven through `app.inject()`, against a temporary library and database. `app.ts`
exists separately from `index.ts` precisely so this is possible without opening a port.

These cover the claims the README makes:

- Every API route refuses a request without a session; login, logout and health are the only
  exceptions.
- Ten login attempts per quarter hour, per source address, so one guesser cannot lock everyone out.
- A viewer gets `403` from every admin route, and a redacted settings object from the one route they
  may read.
- **Walking every id in the library as a restricted viewer returns exactly the permitted photos and
  `404` for all the rest** — the test that the `404`-not-`403` decision exists for.
- Path traversal, absolute paths and symlinks pointing outside the library are all refused, and no
  error response leaks a filesystem path.
- The chunked upload protocol: a replayed chunk answers with the offset the server actually reached,
  a retried finish answers identically twice, a taken name gets ` (1)`, and a cancelled session leaves
  nothing behind.

## Web unit tests

- **`layout`** — that rows justify to the container width, never exceed the target height, never
  enlarge a photo past its own pixels, never span two days, and cover every photo exactly once. Plus
  a guard that a 50 000-photo layout stays far away from anything quadratic.
- **`memories`** — the day window, the equal share across years, stability within a day, and that
  29 February has no counterpart in a common year.
- **`client`** — the binary manifest decoder against records packed exactly as the server packs them,
  including a truncated trailing record and the 2106 timestamp ceiling.
- **`format`** — durations, byte sizes and dimensions.

## End-to-end tests

Playwright drives a real browser against the built server serving a generated library — SQLite index,
worker pool, libvips thumbnailer, built SPA, nothing stubbed. A green run means `npm run build && npm
start` genuinely works.

`e2e/serve.mjs` writes the library and then starts the server, because the server refuses to boot on
a missing `photosRoot` and Playwright launches `webServer` before any global hook. A `setup` project
waits for the first scan to settle and parks a signed-in session for each role.

Specs cover signing in and out, the feed and its virtualisation, day headers, the year rail, the "on
this day" strip, the viewer (keyboard navigation, zoom modes, rotation, downloads), the file browser,
folder creation, a real upload through the browser's file picker, the settings page, and a `mobile`
project on a Pixel 7 profile that checks nothing overflows sideways.

### Notes for anyone adding to these

Two things caught this suite out and will catch the next one:

- **Do not sign out with the shared session.** `ADMIN_STATE` holds one cookie; destroying it
  server-side leaves every later spec unauthenticated. The sign-out spec logs in for itself.
- **The upload spec changes the feed.** Its photo is dated now, so it becomes the newest in the
  library. Anything that depends on a photo's EXIF or size opens one from `Travel/Norway`, which
  nothing writes to, rather than taking whatever is first.

Read the id currently shown in the viewer from `.lightbox-stage img:not(.swipe-peek)` — the neighbour
previews are drawn underneath the current photo during a transition, so `.first()` alone reports
whichever way the stage is moving.

## Continuous integration

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs typechecking and the unit and
integration tests on Ubuntu and Windows, then the end-to-end suite on Ubuntu. The Playwright report
is uploaded as an artifact when it fails.
